# Semantic Console 前后端一致性与界面审计

审计范围：Semantic Console 的项目管理、语义层编辑、知识治理、访问控制及其长列表、代码区和状态反馈。审计原则是不新增产品能力，只校正已有后端能力的前端入口、状态语义和界面约束。

## 分页策略

- 前端分页：规则、SQL Knowledge、模型、字段、Views、Cubes、Cube 内部集合、数据源、Schema 元数据、项目文件和版本。它们由当前接口一次返回完整集合，分页不改变正在编辑的对象。
- 有界服务端窗口 + 前端分页：访问审计。审计数据会持续增长，API 负责限制最多 500 条，页面再按 20/50/100 条分页。后续若需要全历史检索，应单独设计游标接口，不在本次界面修复中扩展功能。
- 不分页：Relationships 地图节点。它是可缩放、可平移的关系画布，不是线性列表；编辑抽屉使用独立滚动。
- 所有分页默认 20 条，可切换 20、50、100 条，显示范围与总数，支持上一页、下一页和页码输入；搜索和筛选改变时回到第一页，删除导致页数减少时自动校正当前页。

## 布局约束

- 桌面端主从工作区使用统一的可视区高度变量，列表、详情、编辑器分别承担自己的滚动。
- Flex/Grid 可收缩子项补齐 `min-height: 0` 与 `min-width: 0`，避免长文本或代码撑开轨道。
- SQL、MDL、Diff 和策略编辑区设置最小/最大高度，内容超出时内部滚动；Instructions 双栏允许主编辑区在断点前正确收缩。
- 低于响应式断点后恢复自然文档流，避免在窄屏上嵌套多个固定高度区域。
- 底部操作区与正文分离，正文滚动区域预留操作区空间。

## 剩余风险

- 当前集合接口除审计外仍是一次性返回；分页解决页面可用性，但不能替代未来的大规模服务端查询设计。
- 关系画布在数百节点场景的性能属于可视化引擎容量问题，不应通过普通分页破坏关系全局视图。
- 生产构建仍提示主包体积超过 500 kB；这是加载性能优化项，不属于本次布局与功能一致性修复。
